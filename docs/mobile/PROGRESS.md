## Phase 6: Sync, offline and resilience

**Status:** in progress. 6a (offline queue) and the maintenance/update refinement are built; local notifications, push (FCM) and
the offline food log are not.

| | |
| --- | --- |
| 6a. Offline queue | Changes made without a connection are kept on the phone and replayed, in order, through `POST /sync/batch`, each with a client-generated op id so the server applies it once. Queued: workout sets, skips, finish and abandon; camera-coach sets; body measurements. Online-first (nothing changes with a connection); queue behind earlier changes to the same workout; conflicts (a newer server copy) and refusals are shown on a Sync screen and never silently overwritten or lost; per account, durable across restarts, kept on sign-out (the sign-out dialog warns); retry after 15 s / 30 s / 1 min / 2 min / 5 min, on foreground, on a new change and on "Sync now". A sync strip appears above the tab bar only when something is waiting. Details: [offline-sync.md](offline-sync.md). |
| Refresh on return | A screen the member left open for 5+ minutes is refreshed from the server when the app comes back to the foreground (dashboard, plan, programmes, nutrition, progress, membership, library), so a plan or content change made on the server appears without a restart; offline, the saved answer stays. 2 widget tests. The content change feed (`/content/changes`) is not used by the app: per-endpoint caching plus this refresh covers the same need with less machinery (a deliberate choice; the feed remains for a future background-sync service). |
| Rest-timer alert (local notification) | Optional (Account → *Rest timer alert*, off until switched on, permission asked at that moment): while the app is in the background during a rest, the phone shows "Rest is over. Next: …" at the engine's absolute end time; rescheduled on +30 s, cancelled on skip / pause / finish / return / sign-out / switch-off; never touches the notification system until enabled.
